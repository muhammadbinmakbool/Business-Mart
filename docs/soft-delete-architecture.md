## 1. Overview

Business Mart ERP uses a **two-tier deletion strategy** to prevent data loss while
preserving the ability to perform emergency permanent deletions under controlled,
audited conditions.

| Mode | Default? | Who Can Use | Reversible? | Audit Logged? |
|------|----------|-------------|-------------|---------------|
| **Soft Delete** | ✅ Yes | All permitted roles | ✅ Yes (restore possible) | ✅ Yes |
| **Hard Delete** | ❌ No — Emergency only | Admin / Super Admin in Destructive Mode | ❌ No | ✅ Yes (mandatory) |

## 2. Core Concepts

### 2.1 Soft Delete (Default)

A **soft delete** marks a record as logically removed without touching the underlying
database row. The record:

- Sets `isDeleted = true`
- Records `deletedAt` (timestamp), `deletedBy` (userId), `deleteReason` (string)
- Remains physically in the database
- Is **excluded from all normal `findMany` queries** via `where: { isDeleted: false }`
- Is **excluded from financial calculations** (the existing business logic already ignores CANCELLED/SUPERSEDED records; soft-deleted records never appear in those queries)

> **Key Rule**: Children are NOT cascade-soft-deleted. Only the parent record is flagged.  
> Child records are already excluded by the parent's isDeleted filter in query joins.

### 2.2 Inactivation vs. Soft Delete (Important Distinction)

These are **separate, independent features**:

| Feature | Field | Purpose | Reversible via UI? |
|---------|-------|---------|-------------------|
| **Inactivation** | `isActive` | Workflow control — prevents new entries linking to this record | ✅ Yes (toggle) |
| **Soft Delete** | `isDeleted` | Logical removal — hides from all lists, reports, calculations | ✅ Yes (database restore) |

A record can be **inactive but not deleted** (still shows in list, just can't be selected).  
A record can be **deleted but technically "active"** (won't show in lists at all).

### 2.3 Hard Delete (Emergency Only)

A **hard delete** permanently removes a database row. It:

- Requires an **active Destructive Mode session** (10-minute JWT cookie)
- Requires **admin password re-confirmation** to activate the session
- Is **fully audited** in the ActivityLog (`action: "HARD_DELETED"`)
- Uses the original cascade deletion logic (preserved in `hardDelete()` repository methods)

## 3. Database Schema

### 3.1 Soft-Delete Fields Added

The following fields were added to all core entity models:

```prisma
isDeleted    Boolean   @default(false)
deletedAt    DateTime?
deletedBy    Int?          // References User.id (not enforced as FK for audit resilience)
deleteReason String?
```

## 4. Destructive Session System

### 4.1 How It Works

```
Admin opens User Dropdown
        │
        ▼
"Enter Destructive Mode" button (admins only)
        │
        ▼
DestructiveModeModal appears
        │
Admin enters password + optional reason
        │
        ▼
enterDestructiveModeAction() called
  → AuthService.verifyCurrentPassword()
  → createDestructiveSession(userId)
    → Signs JWT (HS256) with userId + 10-min expiry
    → Sets HttpOnly cookie "bm-destructive"
  → Logs DESTRUCTIVE_MODE_ENABLED to ActivityLog
        │
        ▼
Destructive Mode Banner appears in Topbar
(red banner with countdown timer + exit button)
        │
        ▼
All hardDelete() calls succeed for 10 minutes
        │
After 10 minutes OR admin clicks "Exit Destructive Mode"
        │
        ▼
exitDestructiveModeAction()
  → Deletes "bm-destructive" cookie
  → Logs DESTRUCTIVE_MODE_DISABLED to ActivityLog
        │
        ▼
All hardDelete() calls throw immediately again
```

### 4.2 Session Library

**File**: `src/lib/destructiveSession.js`

| Export | Purpose |
|--------|---------|
| `createDestructiveSession(userId)` | Creates JWT cookie |
| `validateDestructiveSession(userId)` | Verifies cookie; returns payload or null |
| `deleteDestructiveSession()` | Revokes cookie |
| `assertDestructiveMode()` | Guard function — throws if mode not active |
| `DESTRUCTIVE_SESSION_MINUTES` | 10 (constant) |

**Security properties**:
- Cookie: `HttpOnly`, `SameSite: strict`, `Secure` (in production)
- JWT signed with `process.env.JWT_SECRET`
- `userId` claim verified on every `assertDestructiveMode()` call
- Session is **per-user**: a session started by Admin A cannot be used by Admin B

### 4.3 Server Actions

**File**: `src/modules/auth/controllers/destructiveActions.js`

```js
// Activate (requires password confirmation)
enterDestructiveModeAction(password: string, reason?: string)
  → { success: boolean, message?: string, expiresInMinutes?: number, error?: string }

// Deactivate
exitDestructiveModeAction()
  → { success: boolean, message?: string, error?: string }

// Poll status (safe for client components)
getDestructiveModeStatusAction()
  → { active: boolean, remainingSeconds?: number, expiresAt?: number }
```

### 4.4 Environment Variables Required

```env
JWT_SECRET=<your-secret-key>   # Used for signing the bm-destructive JWT
```

## 5. Repository Layer

### 5.1 Query Filtering Pattern

All `findMany` calls on entities with soft-delete now include:

```js
where: { isDeleted: false, ...otherConditions }
```

`findUnique` calls include `isDeleted: false` in the where clause:

```js
where: { id: parseInt(id), isDeleted: false }
```

> **Exception**: `hardDelete()` internally calls a raw `prisma.entity.delete()` without the
> isDeleted check — this is intentional since it needs to permanently remove the row.

### 5.2 softDelete Method (Standard)

Every repository exposes:

```js
static async softDelete(id, { deletedBy, deleteReason } = {}) {
  return prisma.entity.update({
    where: { id: parseInt(id) },
    data: {
      isDeleted: true,
      deletedAt: new Date(),
      deletedBy: deletedBy || null,
      deleteReason: deleteReason || null,
    },
  });
}
```

**No cascading**. Children are excluded from normal queries via their parent's `isDeleted` filter.

### 5.3 hardDelete Method (Emergency)

Every repository exposes:

```js
static async hardDelete(id, deleteReason) {
  await assertDestructiveMode();  // ← Throws if no active session
  // Original cascade deletion logic preserved here
  return prisma.entity.delete({ where: { id: parseInt(id) } });
}
```

### 5.4 Repository Status Summary

| Repository | softDelete | hardDelete | isDeleted filter in findMany |
|------------|-----------|-----------|------------------------------|
| `PartyRepository` | ✅ | ✅ (+ cascade: advances, intakes) | ✅ |
| `ProductRepository` | ✅ | ✅ (+ constraint checks) | ✅ |
| `IntakeRepository` | ✅ | ✅ (+ cascade: advances) | ✅ |
| `SaleRepository` | ✅ (with audit fields) | ✅ | ✅ (was already there) |
| `SupplierInvoiceRepository` | ✅ | ✅ (DB cascade handles items/adjustments) | ✅ |
| `LedgerRepository` | ✅ | ✅ | ✅ |
| `SalesTrackService` | ✅ | ✅ | ✅ |

## 6. Service Layer

### 6.1 Standard Delete (Soft)

Each service's `deleteX(id, deleteReason)` method:
1. Resolves the current user session to capture `deletedBy`
2. Fetches the existing record (for the ActivityLog description)
3. Calls `Repository.softDelete(id, { deletedBy, deleteReason })`
4. Emits `action: "DELETED"` to ActivityLog

### 6.2 Emergency Delete (Hard)

Each service exposes `hardDeleteX(id, deleteReason)`:
1. Fetches the existing record
2. Calls `Repository.hardDelete(id, deleteReason)` — which internally calls `assertDestructiveMode()`
3. Emits `action: "HARD_DELETED"` to ActivityLog

### 6.3 Special Case: IntakeService

`deleteIntake()` (soft) still triggers `InventoryService.handleIntakeDeleted()` so that
product stock counts remain accurate even after a soft delete. This is critical — an intake
that is soft-deleted must not continue contributing to available stock.

`hardDeleteIntake()` runs the full original transaction (delete advances → delete intake → recalculate stock).

### 6.4 Special Case: SupplierInvoiceService

`deleteInvoice()` (soft):
- Reverts `isSettled: false` on linked SalesTrack entries (so intakes can be re-invoiced)
- Disconnects advances from the invoice (`supplierInvoiceId: null`)
- Then soft-deletes the invoice record

`hardDeleteInvoice()`:
- Performs same advance/track cleanup first
- Then calls `Repository.hardDelete()` (DB cascade removes items and adjustments)

## 8. UI Components

### 8.1 Component Overview

**File**: `src/components/layout/DestructiveModeModal.js`

Exports 3 components:

#### `<DestructiveModeModal onClose onSuccess />`
Full-screen overlay modal for entering Destructive Mode.
- Password input (required)
- Activation reason input (optional)
- Calls `enterDestructiveModeAction(password, reason)` on submit
- Shows inline error on failure

#### `<DestructiveModeBanner onExit />`
Red full-width banner rendered **above** the `<header>` in the Topbar when Destructive Mode is active.
- Shows "Destructive Mode Active" label
- Countdown timer (auto-decrements every second)
- "Exit Destructive Mode" button → calls `exitDestructiveModeAction()`
- Polls `getDestructiveModeStatusAction()` every 30 seconds to catch server-side expiry

#### `<DestructiveModeToggle isDestructiveActive onEnterClick onExit />`
Dropdown menu item in the Topbar user profile dropdown.
- When **inactive**: shows "Enter Destructive Mode" (red, `Shield` icon)
- When **active**: shows "Exit Destructive Mode" (amber, `ShieldOff` icon)
- Only rendered for `ADMIN` and `SUPER_ADMIN` roles

### 8.2 Topbar Integration

**File**: `src/components/layout/Topbar.js`

Changes:
- Added `isDestructiveActive` state, initialized by polling `getDestructiveModeStatusAction()` on mount
- Renders `<DestructiveModeBanner>` above `<header>` when mode is active
- Renders `<DestructiveModeModal>` when `showDestructiveModal` is true
- User avatar icon turns **red** (`text-destructive`, `bg-destructive/20`, red ring) when mode is active

### 8.3 Delete Button Behavior (UI Pattern)

The existing delete confirmation modals/dialogs in registry pages work as follows:

| Destructive Mode State | Delete Button Label | Action Called |
|----------------------|--------------------|--------------------|
| **Inactive** (normal) | "Delete" | `deleteXAction(id, password, reason)` → soft delete |
| **Active** (admin) | "Permanently Delete" | `hardDeleteXAction(id, reason)` → hard delete |

> **Implementation Note**: Individual registry pages must check `getDestructiveModeStatusAction()`
> to dynamically switch button behavior. The `hardDeleteXAction` functions are already exported
> and ready to wire up in each registry's delete confirmation dialog.

## 10. Developer Rules

### ✅ DO

- Always use `softDelete()` (via the relevant service's `deleteX()` method) for normal deletion flows
- Always pass `deleteReason` through from the UI to provide a human-readable audit trail
- Always capture `deletedBy` from the active session before calling `softDelete()`
- Use `assertDestructiveMode()` inside every `hardDelete()` repository method — never bypass it
- Test that `isDeleted: false` filters are present on all new `findMany` queries you write

### ❌ DON'T

- Never call `prisma.entity.delete()` directly in services or controllers — use repository methods
- Never call `hardDelete()` from a standard delete action — it must go through `hardDeleteXAction`
- Never remove the `assertDestructiveMode()` call from any `hardDelete()` method
- Never cascade soft-deletes to children — only the parent entity should be flagged
- Never use `isDeleted` in financial calculations (settlement amounts, ledger totals) — soft-deleted
  records are already excluded because they never appear in query results that feed calculations
- Never store `deleteReason` as required — always optional (`String?` in schema)

### Adding Soft Delete to a New Entity

1. Add the four fields to the Prisma model in both `schema.sqlite.prisma` and `schema.mssql.prisma`:
   ```prisma
   isDeleted    Boolean   @default(false)
   deletedAt    DateTime?
   deletedBy    Int?
   deleteReason String?
   ```
2. Run `npm run prepare:sqlite && npx prisma generate`
3. In the repository: add `where: { isDeleted: false }` to all `findMany` / `findUnique`, add `softDelete()` and `hardDelete()` methods
4. In the service: update `deleteX()` to call `softDelete()`; add `hardDeleteX()` calling `hardDelete()`
5. In the controller: update `deleteXAction(id, confirmPassword, deleteReason)` and add `hardDeleteXAction(id, deleteReason)`
6. In the UI: check `getDestructiveModeStatusAction()` to switch button label and action

## 11. Flow Diagrams

### 11.1 Standard (Soft) Delete Flow

```
User clicks "Delete" on a record
           │
           ▼
Confirmation dialog appears
(shows record name, optional reason field)
           │
User confirms with password
           │
           ▼
deleteXAction(id, password, deleteReason)
           │
           ▼
assertDeletePermission(password)    ← checks role + password
           │
           ▼
XService.deleteX(id, deleteReason)
           │
   ┌───────┴───────┐
   │               │
XRepository      ActivityLog
.softDelete()    .emit("DELETED")
   │
Database row:
isDeleted=true
deletedAt=<now>
deletedBy=<userId>
deleteReason=<reason>
           │
           ▼
Record hidden from all future queries ✅
Record preserved in database ✅
```

### 11.2 Emergency (Hard) Delete Flow

```
Admin clicks "Enter Destructive Mode" in User Dropdown
           │
           ▼
DestructiveModeModal opens
           │
Admin enters password + reason → submits
           │
           ▼
enterDestructiveModeAction(password, reason)
  → verifyCurrentPassword()
  → createDestructiveSession(userId)  ← JWT cookie set (10 min)
  → ActivityLog: DESTRUCTIVE_MODE_ENABLED
           │
           ▼
Red DestructiveModeBanner appears (countdown: 10:00)
           │
           ▼
Admin navigates to a record, sees "Permanently Delete" button
           │
Admin confirms with reason
           │
           ▼
hardDeleteXAction(id, deleteReason)
           │
           ▼
XService.hardDeleteX(id, deleteReason)
           │
           ▼
XRepository.hardDelete(id, deleteReason)
  → assertDestructiveMode()    ← verifies JWT cookie
  → prisma.entity.delete()    ← permanent DB row removal
           │
           ▼
ActivityLog: HARD_DELETED (with reason + userId)
           │
           ▼
Record permanently removed from database ✅
```
